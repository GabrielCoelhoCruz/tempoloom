# Feature parity

This table lists every feature of the reference product that we found in its
public documentation (and, later, in a logged-in test account). See
`docs/clean-room.md` for how evidence is collected and cited.

Status values:

- **done (CalDAV)**: implemented, and a passing full UI E2E test against a
  real CalDAV calendar proves it (real events created, moved and deleted;
  reload and persistence checked). The last column names the tests.
- **done (Google)**: the same proof against a Google Calendar account. None yet.
- **partial**: implemented, but only unit tests prove it, or a part of the
  spec is missing, or (for Google Calendar sync) the Google E2E run is
  pending. The last column says which.
- **blocked**: not implemented yet, or a non-goal. The last column gives the
  reason.

Evidence ids (`E-…`) refer to the private evidence index. Spec links point to
`docs/specs/`.

## Summary

- Rows: 963
- done (CalDAV): 135
- done (Google): 0
- partial: 72
- blocked: 756

"done (CalDAV)" means a full UI E2E test passes against a real CalDAV server (Radicale in a
loopback container): Playwright drives the Tempoloom UI, the real API and scheduler write to the
calendar, and the test checks the calendar, a page reload and persistence. The suite runs in CI
on every push. No row is done on Google Calendar yet: that run needs a service-account key.

Evidence basis: every row comes from public evidence only (marketing pages and help docs). No
logged-in observation of the reference product was made, so behavior that only a logged-in
account shows (exact defaults, API shapes, current-version details) is "public-evidence only";
the open questions in each spec list what is unknown.
